# 회의 일정 조율 제품 플로우

## 목적

현재 프로토타입을 바로 수정하지 않고, 재설계할 수 있다는 전제로 핵심 사용자 흐름을 먼저 고정한다.

이 플로우의 목표는 `주최자가 납득 가능한 회의 시간을 정하고, 참석자는 개인 사유를 과하게 설명하지 않아도 되는 경험`을 만드는 것이다.

## 사용자 역할

### Scheduler

회의를 만들고 최종 시간을 확정하는 사람이다. 이번 과제의 주인공이다.

Scheduler가 해결해야 하는 일은 단순히 빈 시간을 찾는 것이 아니라, 후보 시간 중 어느 시간이 가장 납득 가능한지 판단하고 그 이유를 참석자에게 설명하는 것이다.

### Participant

회의에 초대받아 가능한 시간과 부담되는 조건을 알려주는 사람이다.

Participant는 별도 주인공이라기보다, Scheduler가 좋은 결정을 내리기 위해 고려해야 하는 이해관계자다. 제품은 Participant가 개인 사유를 자세히 말하지 않아도 조건을 전달할 수 있게 해야 한다.

## 핵심 플로우

### 1. 회의 조건 설정

Scheduler가 회의의 기본 조건을 입력한다.

- 회의 제목
- 1시간 회의
- 참석자 6명
- 필수 참석자와 선택 참석자
- 후보 날짜 범위
- 회의 목적

회의 목적은 필수 판단 축이 아니라 후보 정렬의 보조 기준이다.

- 의사결정 회의: 필수 참석자 가능 여부 우선
- 공유 회의: 빠른 확정과 사후 공유 가능성 우선
- 집중 논의: 비선호 시간대와 앞뒤 여유 우선

### 2. 참석자 조건 수집

제품은 기존 캘린더의 free/busy 정보를 먼저 읽고, 부족한 조건만 참석자에게 가볍게 묻는다.

참석자 응답은 네 가지로 제한한다.

- 가능
- 가능하지만 피하고 싶음
- 확인 필요
- 어려움

상세 사유는 선택이다. 기본 공개 범위는 `요약만 공개`다.

예를 들어 `병원`, `육아`, `집중 업무`, `외근 이동` 같은 상세 사유는 그대로 노출하지 않고 다음처럼 바꾼다.

- 비선호 응답
- 업무 일정 충돌 가능성
- 확인 필요
- 불가

### 3. 후보 시간 생성

제품은 가능한 시간대를 단순 나열하지 않고 세 그룹으로 정리한다.

- 바로 확정 가능: 필수 참석자가 가능하고 부담 신호가 거의 없음
- 확인 후 확정: 필수 참석자는 가능하지만 비선호나 확인 필요가 있음
- 피하는 게 좋음: 필수 참석자가 어렵거나 부담 신호가 큼

이 단계에서 점수는 쓰지 않는다. 숫자보다 판단 가능한 상태와 이유가 중요하다.

### 4. 후보 시간 판단

Scheduler는 후보 시간 판단 카드를 본다.

카드 전면에는 세 가지만 보여준다.

- 회의 성립 여부: 필수 참석자가 가능한가
- 부담 신호: 비선호, 업무 충돌 가능성, 확인 필요가 있는가
- 다음 액션: 바로 확정, 1명 확인 후 확정, 다른 후보 비교

카드 상세에서는 선택 참석자 영향, 사후 공유 가능성, 공개되지 않는 상세 사유 수, 회의 목적에 따른 정렬 이유를 볼 수 있다.

### 5. 필요한 확인만 요청

확인이 필요한 후보라면 Scheduler가 특정 사유를 캐묻는 대신, 제품이 최소 확인 요청을 만든다.

예시:

> 이 시간은 필수 참석자가 모두 가능하지만 확인 필요 응답이 1건 있어요. 확정 전에 한 번만 확인해볼까요?

참석자에게는 개인 사유를 다시 쓰라고 하지 않는다. 가능한지, 어렵다면 다른 후보를 선호하는지만 묻는다.

### 6. 최종 확정

Scheduler가 후보를 선택하면 제품은 확정 이유를 함께 만든다.

예시:

> 필수 참석자가 모두 가능하고, 비선호 응답이 없는 시간이라 이 시간으로 확정했어요. 선택 참석자 1명은 사후 공유로 보완할 수 있어요.

확정 문구는 개인 사유를 노출하지 않는다. 팀이 이해해야 하는 것은 `누가 왜 어려웠는지`가 아니라 `왜 이 시간이 합리적인 선택인지`다.

## 화면 단위

### A. 회의 만들기

- 기본 정보 입력
- 참석자 추가
- 필수/선택 참석자 지정
- 회의 목적 선택
- 후보 범위 설정

### B. 참석자 응답

- 후보 시간 확인
- 네 가지 상태 중 선택
- 상세 사유 선택 입력
- 기본 공개 범위 안내

### C. 후보 시간 비교

- 후보 카드 목록
- 바로 확정 가능, 확인 후 확정, 피하는 게 좋음 그룹
- 카드 전면 3요소
- 카드 상세 펼쳐보기

### D. 확인 요청

- 확인 필요 후보 선택
- 익명화된 확인 요청 문구
- 참석자 재응답

### E. 확정 및 공유

- 최종 시간 선택
- 확정 이유 자동 요약
- 참석자에게 공유
- 사후 공유가 필요한 참석자 표시

## 프로토타입 범위

### 반드시 보여줄 것

- Scheduler가 회의 조건을 만드는 흐름
- Participant가 부담 없이 조건을 전달하는 흐름
- 후보 시간 판단 카드
- 확정 이유 공유 문구

### 나중으로 미룰 것

- 실제 캘린더 API 연동
- 복잡한 회의실 예약
- 반복 일정 전체 관리
- 모든 회의 목적별 상세 알고리즘
- AI 자동 확정

## 다음 결정 질문

- 참석자 응답 화면을 실제 프로토타입에 포함할 것인가, 아니면 설명용 화면으로만 둘 것인가?
- 후보 카드는 3개만 보여줄 것인가, 전체 후보를 그룹으로 보여줄 것인가?
- 회의 목적 선택은 첫 화면에 둘 것인가, 후보 정렬 옵션으로 둘 것인가?
- 기존 WORKS 스타일을 유지할 것인가, 아니면 토스 과제 제출용으로 완전히 새 정보 구조를 만들 것인가?
